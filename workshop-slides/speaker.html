Git worktrees have been around since Git 2.5 (2015). Most people don't know they exist.

Worktrees

Why worktrees matter for agents

Without worktrees

  • Agents fight over the same files
  • Branch switching chaos
  • Uncommitted changes get trampled
  • One agent at a time

With worktrees

  • Each agent has its own copy
  • Zero file conflicts
  • Parallel work is safe
  • Merge when done
The key insight: isolation is what makes parallelism safe.

Worktree gotchas

You're not on main

If you yarn dev or npm start, make sure you've cd'd into the worktree directory — otherwise you'll be running from main and wondering where your changes went.

.gitignore'd files aren't copied

Files like .env won't exist in the worktree. Copy them manually or use symlinks.

cp .env .claude/worktrees/<name>/.env

Two common surprises when starting with worktrees. Worth flagging before the hands-on so people don't lose time debugging.

Why self-contained? Each worktree session starts with zero context — the prompt has to carry everything the agent needs.

Decomposition is itself a Claude task. Anthropic's docs recommend the interview pattern — Claude interviews you with questions, then writes the spec. Practitioners' sweet spot: 3–5 parallel worktrees before review becomes the bottleneck.

Parallel

Let agents verify their own work

Agents that can check their work finish.
Agents that can't, drift.

  • Give every session a feedback loop — tests to run, a browser to open, a payload to pipe
  • Make "run the tests" part of the plan, not an afterthought
  • Claude Code's creator calls verification "probably the most important thing" for quality

In today's lab: every hook has acceptance criteria — your agent writes the tests, then bash test/run-tests.sh runs the suite. Tell it to make them pass before it reports done.

The most repeated lesson from heavy users: give the agent a way to validate its own output — tests, a browser, a linter. Without it, parallel agents multiply unreviewed mistakes; with it, they converge. This is why the workshop scaffold ships a test harness.

Common pitfalls

⚠

Don't edit shared files across worktrees

Shared config, types, or entry points edited by multiple agents = merge conflicts. Give each agent its own files.

⏰

Start hard tasks first

Complex features need more wall-clock time. Launch them in Wave 1 so they run while you tackle easier tasks.

🔍

Review before merging

Agents make mistakes too. Treat each worktree branch like a PR — read the diff, run the tests, then merge.

04

Hooks: Automate & Enforce

Make the right thing happen, every time.

The new pillar. Worktrees and agents are about parallelism; hooks are about making each session automatically do the right thing.

Hooks

What is a hook?

Claude Code runs your shell command at lifecycle events.

A hook can observe, inject context, or block an action.

Instructions are suggestions. Hooks are guarantees — they always happen, whether or not Claude remembers.

The simplest mental model: at certain moments, Claude shells out to a script you control, hands it JSON, and reacts to what the script says. Land the thesis: hooks are for determinism — things that always happen, rather than things you hope the model chooses to do.

Hooks

The event lifecycle

EventUse it to…
PreToolUseGate or deny a tool before it runs
PostToolUseReact after a tool — format, lint, verify
UserPromptSubmitInspect / augment a prompt
NotificationSurface "needs you" to your environment
Stop / SubagentStopAct when a session / subagent finishes
SessionStart / SessionEndPrime context / clean up

The starter set. There are 30+ events today (PostToolUseFailure, PreCompact, SubagentStart, PermissionRequest, WorktreeCreate…), five handler types — command, HTTP, MCP tool, prompt, agent — and conditional matchers like Bash(rm *). Browse yours with /hooks.

These six are the ones worth knowing first; today's demo uses PostToolUse and SessionStart. Mention the callout briefly: the surface is much bigger now — prompt hooks even let you put a small LLM judgment between Claude and a tool call. Point at code.claude.com/docs/en/hooks for the full list.

Hooks

The contract

# stdin: the event as JSON
{ "hook_event_name": "PostToolUse",
  "tool_name": "Edit",
  "tool_input": { "file_path": "src/app.ts" } }

# control by exit code…
exit 0   # proceed
exit 2   # PreToolUse: block + show stderr to Claude
         # PostToolUse: tool already ran; stderr surfaces to Claude

# …or by JSON on stdout
{ "hookSpecificOutput": { "additionalContext": "…" } }

Registered in settings.json as event → matcher → command

Two ways to talk back: exit codes for allow/block, JSON on stdout for richer control like adding context.

Hooks

You've already seen one

The Agent Orchestrator status you watched all session is driven by a hook.

# ~/.claude/settings.json (simplified)
"Notification", "Stop", "PreToolUse"
   → agent-orchestrator-notify.sh
   → POST session status to a local server

A handful of lines of bash. That's the whole trick.

Tie it back to the orchestrator demo from earlier. The "magic" status updates are just a Stop/Notification/PreToolUse hook POSTing to a local endpoint.

Hooks

Gotchas & safety

  • Hooks run arbitrary commands with your credentials — review before wiring one in
  • They fire on every matching event — keep them fast
  • Scope the matcher tightly so they only run when relevant
  • Test against a sample payload before keeping one
  • They buy determinism, not keystrokes — fired at the wrong moment they just burn context

The upside: hooks turn soft policy ("don't commit secrets") into hard enforcement. Auto mode gives you a classifier-run version of this for permissions out of the box — guards you write remain the hard floor.

Be honest about the risk: a hook is code that runs automatically with your access. The payoff is real enforcement — exactly what we'll build next. Honest caveat worth naming: Armin Ronacher famously got "no efficiency gains" from hooks because they fired at the wrong granularity and wasted context. Today's lab hooks dodge that critique deliberately — single file, best-effort, exit 0.

Hooks

Pick the right layer

Where should a rule live? Push it as far down the stack as it deserves:

CLAUDE.md Judgment & conventions. Keep it under ~200 lines, and treat it as a living file — every time Claude gets something wrong, add the rule.
↓ Skills Repeatable workflows, loaded on demand. ~8–12 well-chosen skills is the sweet spot before the context tax bites.
↓ Hooks Guarantees. Anything that must always happen — formatting, guards, notifications — belongs here, not in prose.

Instructions drift. Hooks don't.

Bloated CLAUDE.md is the community's #1 anti-pattern — past a few hundred lines adherence quietly collapses. Push automation down: prose for judgment, skills for workflows, hooks for enforcement. For bigger rule sets, .claude/rules/ supports path-scoped files that only load when matching files are touched.

Git worktrees have been around since Git 2.5 (2015). Most people don't know they exist.

Talking points

  • Point to the diagram — one .git, multiple working directories
  • A worktree is a second (or third, or fourth) checkout of the SAME repo
  • Each worktree has its own working directory and branch, but shares the .git history
  • Unlike git clone, worktrees share the underlying git objects — commits, blobs, trees, tags all live in one .git directory. No duplicated history, no extra disk space. That's why creating one is instant.
  • You can cd into any worktree and it's a fully functional git checkout
The key insight: isolation is what makes parallelism safe.

Talking points

  • Without worktrees: Two agents editing the same working directory = race conditions, file conflicts, corrupted state
  • With worktrees: Each agent gets its own directory, own branch, own files — complete isolation
  • "It's the difference between two people editing the same Google Doc vs two people editing their own copies"
  • This is WHY parallel agents work — not magic, just good isolation

Talking points

  • Left (Subagent): Hub-and-spoke. One orchestrator, independent workers, results flow back up. Most token-efficient — each subagent gets its own context window, does its work, and only the final output goes back to the parent. The parent checks the output, which acts as a built-in safeguard.
  • Right (Agent Team): Mesh. Claude's agent teams feature lets teammates work independently in their own context windows and communicate directly with each other — not just back to a lead. You can also interact with individual teammates directly without going through the lead agent.
  • Key advantage of teams: agents can cross-check each other's work and collaborate around the same problem over time. Subagents are fire-and-forget; teammates can challenge, build on, and refine each other's output.
  • The cost trade-off: agent teams run at roughly 7x standard session token usage (every inter-agent message is a model round trip); subagents are much cheaper since only the final output returns to the parent. Use teams when collaboration justifies the cost.
  • "The mesh model is more powerful but harder to control — that's the trade-off."
Agent teams are my go-to for executing implementation plans within a single feature scope.
